## Root cause / model corrections made during design review

Two Phase-1 findings were corrected before implementation (see the task doc's own history for the full reasoning): migration 006's read model was found to resolve down to a single *group*, not "all groups in the program," for non-admin roles; and the audit `actor_role` CHECK constraint gap (§ above) was identified as a hard blocker that static review of RPC authorization alone would have missed, since it only manifests once a staff actor's mutation reaches the audit `INSERT`.

## Cross-program safety

`update_academic_group` and `set_primary_group_membership` are the only two extended RPCs that mutate a row beyond the one directly requested (a group's program can change; a primary promotion can demote another membership in a different program). Both now run a second `resolve_academic_program_editor_mode` check against the second affected program when the actor is professor/program_coordinator, denying the whole operation if that second authorization fails — University Admin/Platform Admin are unaffected. `move_student_group_membership`/`end_student_group_membership` need no second check: the former's own existing business rule already forces the target group into the source membership's program.

## Student eligibility for staff

`add_student_to_group`'s staff-only eligibility check requires a real `academic_profile_contexts` row for the *target program specifically* — active or historical, deliberately not `status='active'`-only, so a student who previously ended a membership in that program remains eligible for staff to re-add, matching TASK 004.6's own zero-active-memberships rule. University Admin/Platform Admin keep the broader, pre-existing university-wide eligibility check unchanged.

## Program assignment lifecycle

`profile_roles` was **not** altered with a `revoked_at`/status column or a new unique constraint, per explicit product correction — it stays the same table every other role on the platform uses, representing only currently-active assignments. Grant inserts one row; revoke deletes that exact row (never bulk); full history is preserved in the new `academic_program_staff_assignment_audit_events` table instead. Concurrent-grant race-safety comes from a transaction-scoped `pg_advisory_xact_lock` keyed on (profile, program, role), not from a schema constraint; an already-existing exact assignment is treated as an idempotent success.

## SECURITY DEFINER lock ordering

Every new/replaced mutation in migration 016 was audited against one rule: no `FOR UPDATE` lock may be acquired on a resource before the actor is confirmed authorized for it, and if authorization was derived from a value that some code path can actually change, that value is re-verified against a fresh, locked read before the mutation proceeds. Two real gaps were found and fixed; the rest were verified already correct:

- **`add_student_to_group`** originally locked the target group before deriving its program and authorizing — fixed: non-locking lookup of `academic_program_id` → authorize → lock → re-verify `academic_program_id` is unchanged (this field is *not* immutable, since `update_academic_group` can move a group between programs) before continuing.
- **`update_academic_group`** locked rows only after authorization already, but never re-verified after the lock that the group's `academic_program_id` still matched what was actually authorized at the top of the function — a concurrent move of the exact same group by another actor between the initial read and the lock would have gone undetected. Fixed: the authorized program id is captured once, and the post-lock re-select now aborts with `40001` if it no longer matches.
- **`set_primary_group_membership`** locked the student's *other* active primary membership — a row that can belong to an entirely different program the actor has no authority over — before running the cross-program authorization check that determines whether touching it is even allowed. Fixed: the other-primary row is now identified via a non-locking lookup first, the cross-program authorization check runs against that, and only then is the row re-selected `FOR UPDATE` (re-validating `is_primary`/`status`, which genuinely can change concurrently, unlike `academic_program_id`).
- **`grant_academic_program_staff_role`** locked the target program before authorizing the caller as University Admin/Platform Admin — fixed with the same non-locking-lookup → authorize → lock → revalidate `organization_id` shape, followed only afterward by locking the target profile, the advisory lock, the existing-assignment check, and the insert + audit.
- **`revoke_academic_program_staff_role`** locked the `profile_roles` row (identifiable by a caller-supplied `assignment_id` alone) before authorizing — fixed the same way. The post-lock revalidation was first written relying on a comment explaining that `scope_type`/`scope_id`/`role_id` are immutable on this table (nothing ever `UPDATE`s a `profile_roles` row, only `INSERT`/`DELETE`); a later pass made this an explicit, non-comment-dependent invariant: the authorized assignment id, scope id, and role id are captured into dedicated variables right after authorization, and the post-lock re-read explicitly compares all four (assignment id, `scope_type = 'program'`, `scope_id`, `role_id`) against them in code, aborting if any no longer match.
- **`move_student_group_membership`** — its *source*-membership authorization was already correctly ordered (non-locking read → authorize → lock → revalidate), but a further pass found the function still locked the *target* group via `FOR UPDATE` before checking whether that group even belonged to the authorized program: an actor authorized only for Program A could momentarily acquire a lock on a Program B group by supplying its id, even though the mutation would later fail on the existing same-program business rule. Fixed: a non-locking lookup now decides both the group's existence and its program match *before* any lock is attempted (reusing the exact pre-existing error messages for each case), and only once both pass is the group re-selected `FOR UPDATE`, with a new post-lock check that aborts with `40001` if a concurrent `update_academic_group` moved it to a different program in the interim.
- **`create_academic_group`**, **`end_student_group_membership`** were audited and found already correct without changes: the first authorizes on a raw input parameter before any lock exists; the second authorizes on `academic_profile_contexts.academic_program_id` (traced across every write in this file and confirmed never reassigned to a different value on an existing row) and has no separate lock step at all, relying correctly on its `UPDATE ... WHERE status = 'active'` clause as an atomic lock-and-guard in one statement.

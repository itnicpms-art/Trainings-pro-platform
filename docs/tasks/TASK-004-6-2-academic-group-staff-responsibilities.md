# TASK 004.6.2 — Professor <-> Academic Group Responsibilities

## Scope

Adds nominal Professor <-> Academic Group responsibility bookkeeping on top of TASK 004.6.1's program-scoped authorization model. This task is **not** about program access — that already comes entirely from `public.profile_roles(scope_type='program', role in (professor, program_coordinator))`, unchanged.

**PROGRAM ASSIGNMENT CONTROLS AUTHORIZATION. GROUP ASSIGNMENT CONTROLS RESPONSIBILITY, NOT ACCESS.** A professor with a valid program-scoped professor role and zero group responsibilities retains every program/group/student capability TASK 004.6.1 already grants — group responsibility never becomes a permission boundary. There is no professor self-request and no approval workflow in this task: Program Coordinator, University Admin, and Platform Admin assign or unassign a professor directly. Migration 016's own header comment describes an older idea for this task ("My groups", professor self-request, coordinator approval); that comment is stale relative to this product decision and is left untouched, since migration 016 is already deployed to production and immutable — the current, authoritative model is stated here and in migration 018 instead.

## Role model

- **Program Coordinator**: primary operational authority at PROGRAM level (`profile_roles` role=`program_coordinator`, scope_type=`program`, unchanged from TASK 004.6.1). May assign/unassign professors to groups only in programs they coordinate. No group-level coordinator concept is introduced — a program with multiple academic programs under one faculty can have a different coordinator per program, exactly as TASK 004.6.1 already allows.
- **Professor**: secondary operational staff. May manage program/group/student data per TASK 004.6.1. May never assign/unassign group responsibility, including their own — `resolve_academic_program_editor_mode` returning `'professor'` is an explicit deny in both new mutation RPCs.
- **University Admin / Platform Admin**: may assign/unassign within their own / selected university, exactly as they already grant/revoke program roles in migration 016.

Cardinality: a professor may be responsible for zero, one, or many groups, across one or several programs (if authorized professor in each); a group may have zero, one, or many responsible professors. No lead/assistant distinction exists.

## Target professor eligibility

A target profile is eligible for Professor <-> Group responsibility only if **all** are true: `profile.status = 'active'`; the profile belongs to the group's university (`profiles.university_id` matches the group's `organization_id`); and the target holds a real, current `profile_roles` row with `role.code = 'professor'`, `scope_type = 'program'`, `scope_id = <the group's academic_program_id>`. `profile_type` alone is never sufficient, and a `program_coordinator` role alone does not satisfy this — if the same profile independently holds both `program_coordinator` and `professor` for the same program, the explicit `professor` row is what makes it eligible.

## Self-target

A Program Coordinator / University Admin / Platform Admin **may** name their own profile as the assigned professor, provided that same profile independently holds a real current professor program role for the target program. No special-case code exists for this: the eligibility check never compares the target profile to the actor, so it is allowed or denied by the exact same rule as any other target. This is administrative/coordinator authority, not professor self-service — a plain `professor` actor_mode can never assign or unassign anyone, including themselves, since `resolve_academic_program_editor_mode` returning `'professor'` is denied before eligibility is even checked. The audit trail always records the actor's real mode (`program_coordinator`/`university_admin`/`platform_admin`), never `'professor'`.

## Data model

`public.academic_group_staff_assignments` (migration 018) — current responsibilities only, no `status`/`revoked_at`/`ended_at`. This mirrors `profile_roles` + `academic_program_staff_assignment_audit_events` (active-row + audit-history), not `academic_profile_contexts` (whose `started_at`/`ended_at` track a real membership timeline this relationship does not have). Unlike `profile_roles`, a real `unique (academic_group_id, staff_profile_id)` constraint is used: this is a new, single-purpose table (not a generic multi-shape RBAC table shared by every role on the platform), so DB-enforced uniqueness is simpler and safer than an advisory-lock-only discipline for the duplicate-assign race specifically. A compound FK `(academic_group_id, organization_id, academic_program_id) -> academic_groups(id, organization_id, academic_program_id) on delete restrict` structurally ties every row to the exact organization/program of its group, mirroring `academic_profile_contexts_group_same_program_fk`'s existing pattern.

`public.academic_group_staff_assignment_audit_events` (migration 018) — immutable, matching the established audit-table shape exactly. `actor_role` allows `university_admin`/`platform_admin`/`program_coordinator` (never `professor`) — unlike `academic_program_staff_assignment_audit_events`, which excludes `program_coordinator` since only admins grant/revoke PROGRAM-level roles; a Program Coordinator is a legitimate actor for GROUP-level responsibility. `action` allows `assign`/`unassign`/`cleanup_on_program_role_revoke`. `assignment_id` has no foreign key, since unassign and cleanup both delete the live row.

RLS: enabled on both tables, zero policies, `revoke all ... from public, anon, authenticated` on each, matching every table from migration 004 onward. All access is through `SECURITY DEFINER` RPCs.

## Assign / unassign RPCs

`assign_professor_to_academic_group(requested_profile_id, target_academic_group_id, target_profile_id)` and `unassign_professor_from_academic_group(requested_profile_id, assignment_id)` (migration 018), both `SECURITY DEFINER`. Both share one lifecycle serialization key — `pg_advisory_xact_lock(hashtext(profile::text||':'||program::text), hashtext('professor'))`, the same shape `grant_academic_program_staff_role`/`revoke_academic_program_staff_role` already use — held for the rest of the transaction, so a concurrent grant/revoke of the target's own professor authorization, or a concurrent assign/unassign for the same profile+program, cannot interleave.

Assign's lock order: non-locking group lookup -> authorize actor via `resolve_academic_program_editor_mode` (deny `42501` if the result is `'professor'`) -> acquire the advisory lock -> lock the group row `FOR UPDATE` -> revalidate group/program/organization unchanged and group still `active` -> verify the academic program is `active` -> verify the target profile (active, same university, real current professor role, read fresh under the advisory lock — never `profile_type`) -> `insert ... on conflict (academic_group_id, staff_profile_id) do nothing returning ...`. If a row was actually inserted, exactly one `assign` audit event is written; on conflict, the existing row is fetched and returned with `already_existed: true` with no additional audit event — no exception-based idempotency anywhere. Because the advisory lock is held for the whole transaction and `unassign_professor_from_academic_group` takes the identical key before deleting a row, the existing row cannot be concurrently removed between the conflicting insert and the fallback read.

Unassign always succeeds regardless of group/program active/inactive/archived status (cleanup must remain possible), locates the exact row non-locking first, authorizes, takes the same advisory lock, locks and revalidates the exact row, deletes it, and writes one `unassign` audit event. A second unassign of an already-gone row returns a clean not-found error, mirroring `revoke_academic_program_staff_role`'s existing idiom.

## Program-role revoke integration

`revoke_academic_program_staff_role` (migration 018, `create or replace`, same signature; migration 016 untouched). Steps 1-3 and 5-7 (non-locking lookup, authorize, capture authorized values, lock-and-revalidate the exact `profile_roles` row, delete, audit) are unchanged from migration 016. Two new steps: if the revoked role is `professor`, the shared professor-lifecycle advisory lock is acquired **before** the exact `profile_roles` row is locked (not after) — this keeps lock order identical to `assign_professor_to_academic_group`'s (advisory lock first, row lock second) and never holds a row lock while waiting on the advisory lock. After the delete, and still under that lock, the function checks whether **another** real current professor role row exists for the same profile+program — `profile_roles` intentionally has no unique constraint (TASK 004.6.1), so a second professor row for the same profile+program is not schema-impossible. Group responsibilities are cleaned up (deleted, one `cleanup_on_program_role_revoke` audit event per row, `actor_role` = the revoking admin's own mode) **only** when no professor role remains. Revoking a `program_coordinator` role never triggers this path at all. No exception handler exists anywhere in the function: a failure in any statement, including any audit insert, aborts the entire transaction — the program-role revoke and every cleanup delete/audit pair succeed together or not at all.

Final invariant: active group responsibility exists only while at least one real current professor program authorization exists for that profile/program.

## Cross-program group-move integration

`update_academic_group` (migration 018, `create or replace`, same signature; migration 016 untouched otherwise). Every TASK 004.5/004.6.1 invariant and lock-order fix already in migration 016 is preserved verbatim. One new guard: once the group row is locked and revalidated (the existing step), if `target_academic_program_id` differs from the group's current program **and** the group has any row in `academic_group_staff_assignments`, the whole update is denied (`22023`, "Cannot move an academic group with active professor responsibilities"). No responsibility is ever auto-deleted, silently migrated, or re-evaluated against the target program's eligibility — the operator must explicitly unassign every professor first, then move the group. The group row is already locked by this point, so this is naturally serialized against a concurrent `assign_professor_to_academic_group` call for the same group (which also locks this exact row before inserting).

## Read model

Two independent existing read paths both need this data — sharing the `AcademicGroupsEditor` UI component does not mean they share a backend RPC. `get_program_staff_academic_overview` (Professor/Program Coordinator, single-program-scoped) and `get_academic_groups_editor_overview` (University Admin via `getAcademicGroupsEditor`, Platform Admin via `getAdminAcademicGroupsEditor` delegating to the same wrapper, university-wide-scoped) are both `create or replace`d with unchanged signatures, both gaining the same two logical fields:

- `group_staff_assignments: { id, academic_group_id, academic_program_id, staff_profile_id, staff_display_name, assigned_by_profile_id, created_at }[]`
- `eligible_professors: { academic_program_id, profile_id, display_name }[]`

In `get_program_staff_academic_overview`, when `actor_mode = 'professor'`, `group_staff_assignments` is filtered in SQL to `staff_profile_id = requested_profile_id` and `eligible_professors` is the literal `[]` without its query ever running (a SQL `CASE` whose else-branch subquery never evaluates for that actor mode) — enforced server-side, not left to the UI to hide. `program_coordinator`/`university_admin`/`platform_admin` see every responsibility and every eligible professor in the selected program. `get_academic_groups_editor_overview` never actually authorizes a `'professor'` actor_mode today, so its two new fields are always the full, unfiltered university-wide scope.

## UI

No new top-level route. `AcademicGroupsEditor` (already shared by University Admin's own page, Platform Admin's `/admin/academic-structure`, and the professor/coordinator section via `adaptProgramStaffOverview`) gains two new optional props (`groupStaffTranslations`, `groupStaffAction`, mirroring the existing `membershipOverview`/`membershipTranslations`/`membershipAction` pattern) and renders a new `AcademicGroupStaffPanel` per group, alongside the existing `GroupMembershipPanel` slot. The component itself decides whether to forward the action down to the panel based on `overview.actor_mode === 'professor'` — so every page can pass the mutation action unconditionally, and a plain professor always gets a read-only badge list (no assign form, no eligible-professor roster, no unassign button) regardless of what the caller passes; `resolve_academic_program_editor_mode` would deny them at the RPC layer regardless, so this is defense in depth, not the actual authorization boundary. "My groups" is a client-side filter over the group list already fetched, comparing each group's `group_staff_assignments` against `overview.actor_profile_id` — no new fetch, no new RPC, shown only when `overview.actor_mode === 'professor'`. A professor with zero responsibilities still sees and manages every group TASK 004.6.1 already grants them; "My groups" is simply empty.
